How to Develop an Image Classifier

This is a project that aims to demonstrate the modern practices of machine learning development using image classification as an example. It is intended to be as a practical example of ML System Lifecycle.

Pre-requisites

We install the following tools system-wide:

  • Git
  • git-lfs
  • Conda
  • uv
  • dvc
  • infisical

We prepare a folder as the root of the project.

mkdir example-classifier
cd example-classifier

Replicate the following structure:

.
├── docker-compose.yml
├── README.md
├── server
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── test     # Unit tests.
│   ├── script   # Convenient development scripts.
│   ├── notebook # Exploratory visulisations and analysis.
│   └── src
│       └── example_server
│           ├── main.py    # FastAPI app entry point.
│           ├── predict.py # or generate.py, depending on the task.
│           └── schemas.py
└── trainer
    ├── data
    │   └── raw
    ├── Dockerfile # One-shot container following 'general' pattern for pre-processing, training, and tuning.
    ├── dvc.yaml
    ├── notebook
    ├── params.yaml
    ├── pyproject.toml
    ├── test     # Unit tests.
    ├── script   # Convenient development scripts.
    ├── notebook # Exploratory visulisations and analysis.
    └── src
        └── example_trainer
            ├── dataloader.py
            ├── dataset.py
            ├── evaluate.py
            ├── model.py
            ├── preprocess.py
            ├── train.py
            └── tune.py

Initalise Git. Add .gitignore and .gitattributes files. Use gitignore to find the .gitignore file. Use gitattributes to find the .gitattributes file.

git init
git lfs install

Define the Conda environment using the environment.yml file.

name: example-classifier
channels:
  - defaults
dependencies:
  - python=3.11
  - pip

Create the Conda environment.

conda env create -f environment.yml
conda activate example-classifier

Create uv project and remove main.py.

cd trainer
uv init
rm main.py
cd ../server
uv init
rm main.py

Setup Infisical account. Then, log in to Infisical and initialise it in the project root.

infisical login status
infisical login
infisical user switch
infisical init

Setup DagsHub account. For S3, endpoint URL, region, and credentials use DagsHub repo page and the Infisical secrets:

dvc init
dvc remote add origin s3://bucket-name
dvc remote modify origin endpointurl https://dagshub.com/api/v1/repo-buckets/s3/username
dvc remote modify origin region us-east-1
infisical run -- bash -lc 'dvc remote modify --local origin access_key_id "$DAGSHUB_TOKEN"'
infisical run -- bash -lc 'dvc remote modify --local origin secret_access_key "$DAGSHUB_TOKEN"'
dvc remote default origin

Install the main dependencies that are used to develop the model:

uv pip install torch torchvision mlflow optuna pandas scikit-learn matplotlib jupyterlab nbstripout torchcam ipywidgets

Frame

Let's pretend that we are working in a company that is sorting images into different categories. To improve the speed of this process, we are developing an image classifier that can automatically categorise images. Additionally, we want to keep the process energy efficient, timely and carbon-aware.

The work starts from problem definition. The objective is to frame the problem into an established task and define the appropriate metrics. In this case, the task is image classification. The appropriate metrics are performance, duration, energy consumption, emissions.

Performance is measured in terms of accuracy as the primary metric. Precision, recall, F1 score, and confusion matrix are secondary metrics. Duration is measured in seconds. Energy consumption is measured in kWh. Emissions are measured in kg CO2e.

Importantly, we set a threshold of accuracy to 75% on test data as a way to constitute a success. Finally, the information at this stage would typically be documented in project deliverables.

Data

At this stage, we collect data. The data could be collected using external services, generated internally, or sourced from existing datasets. For this example, we will use a publicly available dataset that we download manually in a zip file to Downloads folder. We extract the contents to data/raw/animals10 folder under the project root. Then, to track the raw data with DVC:

dvc add data/raw/animals10

Then, to push the raw data to DagsHub:

dvc push

Use Jupyter Lab for raw data exploration. Save the notebooks under notebooks/ folder under the project root. Notebooks that load MLflow models need the Infisical prefix so the tracking URI is available:

infisical run -- jupyter lab

Install a git hook that automatically strips output cells (and execution counts) from Jupyter notebooks before each commit.

nbstripout --install

The main objective is to make sure that the data is suitable for the training by implementing a preprocessing script under src/preprocess.py that transforms the raw data into a format suitable for training and saves it to data/processed/<dataset_name> folder under the project root. This is achieved, first by exploring the data in the notebooks, then by saving the implementation to the script.

dvc stage add -n preprocess \
  -d src/preprocess.py \
  -d data/raw/ \
  -o data/processed/ \
  -p params.yaml:preprocess \
  image-classifier-preprocess src/preprocess.py

Add parameters to params.yaml.

preprocess:
  low_pct: 5.0
  high_pct: 95.0
  train_split: 0.65
  validation_split: 0.15
  test_split: 0.20
  seed: 42

Run the entire pipeline:

dvc repro

The entire stage becomes a one-shot Docker container that downloads the raw data, preprocesses it, tracks and pushes the data using DVC.

Train

At this point, the objective is to create CLI scripts: src/train.py, src/evaluate.py, src/tune.py, and src/predict.py. The tuning script is left out of the pipeline. It finds the best parameters which are then used to train the model.

We use MLflow to track and compare the experiments. Every run we log train/val metrics. A practical workflow is depicted below.

every run  → log train/val metrics
           → compare runs using val accuracy
           → pick best model

Evaluate

During the evaluation, we use test data split. It is there to ensure that the model is evaluated on data it has not seen before. We register a model automatically but only when a threshold is met and the accuracy is higher than the best registered accuracy. We use MLflow for model registry. A practical workflow is depicted below.

once       → evaluate best model on test set
           → log test metrics + confusion matrix to that run
           → if accuracy > threshold and accuracy > best registered accuracy:
               → convert to ONNX
               → register ONNX model in MLflow

The train and evaluate stages become a one-shot Docker container that trains the model, evaluates it on the test set, and registers the model in MLflow if the accuracy meets the threshold.

Package

The objective is to ensure reproducibility via versioning. This is achieved by utilising MLflow model registry mechanism that allows us to track individual model versions pushed during the evaluation.

Serve

Deploy the ONNX model using ONNX Runtime. Triton Inference Server is used to serve the model. The model is served behind FastAPI.

The entire stage becomes a persistent Docker container that serves the model via FastAPI with Triton Inference Server and ONNX Runtime in the background.

Optimise

The objective is to optimise the serving after the deployment. Compare different deployment backends such as PyTorch vs ONNX Runtime in terms of performance and resource usage.

Test

The objective is to automate testing the deployed model. Use CI to run automated tests.

Operate

The objective is to monitor the status of the deployment using Prometheus and Grafana.

Communicate

The objective is to tell the stakeholders about the deployment status and performance.
